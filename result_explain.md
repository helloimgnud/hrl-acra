# Comprehensive Guide to HRL-ACRA Training Outputs & Evaluation Metrics

This document provides a detailed explanation of all training outputs, logs, metrics, checkpoints, and evaluation results generated by the Hierarchical Reinforcement Learning Admission Control (HRL-AC) solver. 

## 1. Overview of the HRL + PPO Training Pipeline

The training pipeline implements a Hierarchical Reinforcement Learning (HRL) architecture combined with Proximal Policy Optimization (PPO). It splits the Virtual Network Embedding (VNE) problem into two levels:

1.  **High-Level Admission Control (PPO Agent):** The high-level agent observes the current Physical Network (substrate) state and the incoming Virtual Network Request (VNR). It outputs a binary decision: **Accept** or **Reject**. This agent is trained using PPO, learning to maximize long-term rewards (revenue) while avoiding bottlenecks and map-failures.
2.  **Low-Level Node/Link Mapping (Sub-Solver):** If the high-level agent accepts the request, it is passed to a low-level solver (e.g., `nrm_rank`, `fast_hpso`). The sub-solver performs the actual node and link mapping. 
    *   If mapping is successful, the VNR is embedded, resources are allocated, and a positive reward (based on revenue and cost) is returned to the high-level agent.
    *   If mapping fails, resources are unchanged, and a negative penalty is returned to penalize the high-level agent for a poor admission decision.
    *   If the high-level agent decides to reject the VNR, it is immediately discarded (Early Rejection), saving computation time. A small shaped penalty/reward is returned.

## 2. Explanation of Saved Artifacts and Directory Structure

When running the training command, an output directory is generated under `save/hrl_ac/[run_id]-[timestamp]`.

### 2.1. `log/` Directory (TensorBoard & Training Info)
*   **`events.out.tfevents.*`**: TensorBoard event files. These store real-time training metrics (loss, value estimates, entropy, reward) which can be visualized using `tensorboard --logdir save/hrl_ac/`.
*   **`training_info.csv`**: Contains episode-by-episode RL-specific metrics like actor loss, critic loss, and entropy.

### 2.2. `model/` Directory (Model Checkpoints)
*   **`model-<epoch>.pkl`**: Saved state dictionaries (weights) of the PPO actor and critic neural networks (GNNs). Saved every `--save_interval` epochs. 
*   **Usage:** Used for resuming training or evaluating a specific epoch's performance during testing.

### 2.3. `records/` Directory (Evaluation Detail CSVs)
*   **`hrl_ac-[run_id]-[timestamp].csv`**: Generated every `--eval_interval`. Contains the step-by-step VNE simulation details (each VNR's outcome, cost, and revenue) during an evaluation pass on the test dataset. Useful for deep-diving into why a specific request failed.

### 2.4. `config.yaml`
A snapshot of the configuration (Hydra dictionary) used for the run, ensuring reproducibility.

### 2.5. Main Summary CSV (`exp-wx_100-hrl_ac-training.csv`)
The primary output file summarizing the final evaluation performance of the model across different epochs.

## 3. CSV Metrics & Fields Explanation

Below is a detailed breakdown of the fields found in the summary CSV file (`exp-wx_100-hrl_ac-training.csv`):

### 3.1. Admission and Success Metrics

*   **`acceptance_rate`**
    *   **Meaning:** The ratio of successfully embedded VNRs to the total number of arrived VNRs.
    *   **Computation:** `success_count / total_arrived_requests`
    *   **Goal:** Higher is better. Reflects overall mapping success.
    *   **Time Progression:** Should steadily increase as the agent learns better admission strategies, converging at a stable high.
    *   **Abnormal Behavior:** A sudden drop or sticking at `0.0` means the agent learned a degenerate "always reject" policy or mapping is failing entirely.

*   **`success_count`**
    *   **Meaning:** Absolute number of VNRs successfully embedded.
    *   **Goal:** Higher is better.

*   **`early_rejection_count`**
    *   **Meaning:** Number of VNRs rejected explicitly by the PPO high-level agent.
    *   **Goal:** Optimal balance. Too high = overly conservative policy. Too low = agent accepts everything, leading to resource exhaustion.
    *   **Time Progression:** Usually starts high (safe exploration) and decreases as the agent learns which requests are actually mappable.

*   **`place_failure_count` & `route_failure_count`**
    *   **Meaning:** `place_failure` counts node mapping failures. `route_failure` counts link mapping (shortest path) failures.
    *   **Goal:** Lower is better. 
    *   **Reflection:** If these are high, the PPO agent is making bad admission decisions (accepting VNRs that the sub-solver cannot map). The agent should learn to "early reject" these instead.

### 3.2. Financial and Efficiency Metrics

*   **`r2c_ratio` (Revenue-to-Cost Ratio)**
    *   **Meaning:** The efficiency of the network embeddings. 
    *   **Computation:** `total_revenue / total_cost`
    *   **Goal:** Higher is better. A value close to 1.0 means links are mapped efficiently (short paths).
    *   **Time Progression:** Should improve as the agent learns to prioritize efficient requests.

*   **`total_revenue` & `total_cost`**
    *   **Meaning:** Revenue is the theoretical value of the requested CPU/Bandwidth. Cost is the actual physical resources consumed (longer paths = higher cost).
    *   **Goal:** Maximize revenue while minimizing cost.

*   **`long_term_aver_revenue` / `long_term_aver_cost`**
    *   **Meaning:** The average revenue/cost generated per time unit over the entire simulation duration.
    *   **Goal:** Higher revenue and lower cost are better. This is the ultimate metric for measuring VNE profitability.

### 3.3. Resource Utilization Metrics

*   **`min_p_net_available_resource`, `min_p_net_node_available_resource`, `min_p_net_link_available_resource`**
    *   **Meaning:** The minimum available bottleneck resources observed during the simulation.
    *   **Goal:** Lower values mean higher utilization (which is good for profit), but hitting absolute `0` means the network is severely congested.
    *   **Reflection:** Indicates if the agent is balancing load properly. If node resources are exhausted but link resources are high, the mapping strategy (sub-solver) might be poorly balanced.

*   **`max_inservice_count`**
    *   **Meaning:** The maximum number of VNRs running concurrently on the physical network at any given time.
    *   **Goal:** Higher is better (higher concurrency means better packing).

### 3.4. Reinforcement Learning Metrics

*   **`cumulative_reward`**
    *   **Meaning:** The total RL reward accumulated by the PPO agent over the evaluation episode.
    *   **Computation:** Sum of shaped rewards (e.g., `+Revenue/Cost` for success, `-Penalty` for failures).
    *   **Goal:** Higher is strictly better. 
    *   **Time Progression:** Must follow an upward trend during training. 
    *   **Abnormal Behavior:** Large negative values mean the agent is constantly failing mappings. `NaN` indicates numerical instability in the GNN or reward function.

### 3.5. Metadata

*   **`solver_name`, `seed`, `p_net_dataset_dir`, `v_nets_dataset_dir`**: Identifies the configuration used.
*   **`run_id`, `start_run_time`, `clock_running_time`**: Tracking metadata. `clock_running_time` indicates the wall-clock time for the evaluation.

## 4. Interpretation of Training Stages

1.  **Early Stage (Epochs 0-10):** 
    *   **Characteristics:** High `early_rejection_count`, low `acceptance_rate`, highly negative or fluctuating `cumulative_reward`.
    *   **Interpretation:** The agent is exploring. Since failures carry heavy penalties, the agent often defaults to "rejecting everything" to stay safe.
2.  **Middle Stage (Epochs 10-30):**
    *   **Characteristics:** `acceptance_rate` climbs, `early_rejection_count` drops. `place/route_failure_counts` might spike briefly as the agent explores accepting more requests. `cumulative_reward` begins a steady upward trend.
    *   **Interpretation:** The agent is learning the mapping boundary, discovering which graph structures lead to successful embeddings and positive rewards.
3.  **Convergence Stage (Epochs 30+):**
    *   **Characteristics:** `acceptance_rate` plateaus at a high level. `cumulative_reward` stabilizes. `early_rejection_count` balances perfectly with the network's capacity.
    *   **Interpretation:** The policy has converged. The model accurately predicts the sub-solver's success probability and network capacity.

## 5. Identifying the Best Trained Model

To select the best checkpoint for deployment/testing:
1.  Open `exp-wx_100-hrl_ac-training.csv`.
2.  Sort by **`acceptance_rate`** (Primary) and **`long_term_aver_revenue`** (Secondary) in descending order.
3.  Ensure that for the top runs, **`r2c_ratio`** is reasonable (> 0.45 in typical Waxman topologies) to ensure it isn't wasting resources.
4.  Find the corresponding row's epoch (row index corresponds to evaluation intervals).
5.  Retrieve the matching `model-<epoch>.pkl` from the `model/` directory.

## 6. Troubleshooting Guide for Unstable Training

If the metrics exhibit abnormal behavior, consult the following guide:

*   **Symptom: `cumulative_reward` is `NaN` or Model crashes with `NaN` loss.**
    *   *Cause:* Gradient explosion in the GNN layer, or dividing by zero in state normalization.
    *   *Fix:* Check `virne/solver/learning/rl_core/tensor_convertor.py`. Ensure orthogonal weight initialization is used in the GAT network. Check for zero-capacity nodes/links in the substrate dataset.

*   **Symptom: `acceptance_rate` remains exactly 0.0 (Agent rejects everything).**
    *   *Cause:* The failure penalty is too high compared to the success reward. The agent falls into a local optimum of "safe rejection".
    *   *Fix:* Adjust the reward shaping. Increase the positive reward coefficient or reduce the explicit failure penalty. Ensure Baseline Subtraction (Advantage Normalization) is correctly applied across parallel environment instances.

*   **Symptom: High `acceptance_rate` but extremely high `place/route_failure_count`.**
    *   *Cause:* The agent is accepting everything unconditionally; it has not learned to differentiate network states.
    *   *Fix:* The observation features might not adequately represent the network bottlenecks. Check the GNN feature construction. Ensure the agent's action space (Accept/Reject) is properly masking invalid actions if capacity is hard-limited.

*   **Symptom: Training is extremely slow.**
    *   *Cause:* PPO trajectory collection is bottlenecked by the `nrm_rank` sub-solver on large graphs.
    *   *Fix:* Increase the number of parallel workers (`num_workers`) in `config.yaml`, or switch to a faster heuristic sub-solver for early training epochs.
